## Retesting Past Mistakes & Recent Gotchas (Cold Evaluation)

The following questions pull directly from recurring themes in `mistakes.md` and critical architectural lessons learned during Chunks 11–15.

### Question 1: SQLite Foreign Key Constraints & Cascade Deletions
*Why does SQLite ignore `ON DELETE CASCADE` by default, and how did we ensure that deleting a parent `routes` record reliably deletes all of its associated `route_points` in Drift?*

> **Answer**:
> By default in SQLite (for backward compatibility with SQLite 2.x), foreign key constraint enforcement is completely disabled. If a database is opened without explicitly enabling foreign keys, SQLite treats foreign key declarations as documentation and will not trigger cascade deletes or enforce foreign key integrity checks.
>
> In Drift, we solved this at two distinct layers:
> 1. In `AppDatabase.migration.beforeOpen`, we execute `await customStatement('PRAGMA foreign_keys = ON;');` so that SQLite actively enforces foreign keys for every database connection.
> 2. In `deleteRoute(id)`, we implemented defensive transaction wrapping:
>    ```dart
>    Future<void> deleteRoute(String id) async {
>      await transaction(() async {
>        await (delete(routePoints)..where((tbl) => tbl.routeId.equals(id))).go();
>        await (delete(routes)..where((tbl) => tbl.id.equals(id))).go();
>      });
>    }
>    ```
> This ensures that even under custom test configurations, orphan breadcrumb points can never leak into flash storage.

### Question 2: The Longitude-First Standard in PostGIS & GeoJSON
*What coordinate order does GeoJSON and PostGIS WKT mandate, how does it differ from standard colloquial speech, and what catastrophic bug occurs if you invert them?*

> **Answer**:
> In colloquial language and most mobile location SDKs (e.g. `Position.latitude, Position.longitude`), coordinates are expressed as $(y, x)$ — Latitude first, Longitude second.
>
> However, international spatial standards (OGC, PostGIS, WKT, GeoJSON) strictly adhere to standard Cartesian $(x, y)$ coordinate geometry, which mandates **Longitude first, Latitude second**:
> - **GeoJSON**: `[longitude, latitude]`
> - **WKT**: `POINT(longitude latitude)` or `LINESTRING(lon1 lat1, lon2 lat2, ...)`
>
> If a developer inverts them (writing `[latitude, longitude]`), the coordinates are mapped with axes flipped. For example, coordinates for New York City (`40.7128° N, 74.0060° W`) become `[-74.0060° Lat, 40.7128° Lon]`, plotting the user's route in the Antarctic ocean near Queen Maud Land, and causing PostGIS spatial indexes (GiST) and distance queries to calculate nonsensical spatial relationships.

### Question 3: GPS Point Buffering vs Direct SQLite Writes
*Why is writing every GPS point directly to SQLite an anti-pattern on mobile devices, and how does in-memory batch buffering solve both battery and I/O degradation?*

> **Answer**:
> GPS hardware emits 1 to 2 readings per second. If an application executes `INSERT INTO route_points` on every tick, each insert initiates an individual SQLite disk transaction: opening a WAL frame, writing to disk, and executing an OS `fsync` call. Over an hour-long run (3,600 to 7,200 points), this causes:
> - Severe battery drain from constant flash storage controller wake-ups.
> - Premature NAND flash storage wear.
> - UI thread micro-stutters from database lock contention.
>
> Our solution buffers incoming coordinates in an in-memory Dart list (`_buffer`). Coordinates are flushed to disk using Drift's atomic batch API (`batch.insertAll`) only when the buffer reaches 10 points or every 10 seconds, or upon pause/finish. This reduces 3,600 disk transactions to fewer than 360 batch operations (a 90% reduction in disk I/O) while ensuring that at most 10 seconds of breadcrumbs are ever at risk in a sudden crash.

### Question 4: Partial Updates in Drift vs `insertOnConflictUpdate`
*Why does `insertOnConflictUpdate(companion)` fail when attempting partial updates (such as updating only a route's status or end time), and what is the correct Drift pattern?*

> **Answer**:
> `insertOnConflictUpdate` is an upsert that evaluates both the `INSERT` branch and the `UPDATE` branch. For the `INSERT` branch to compile and validate, the Companion must provide values for **all non-nullable columns without defaults**. If you supply a companion that only specifies `status` and `updatedAt`, Drift rejects the companion because it lacks mandatory columns like `id` and `startTime`.
>
> For partial updates to existing records, you must always use Drift's targeted update query:
> ```dart
> (update(routes)..where((tbl) => tbl.id.equals(id))).write(
>   RoutesCompanion(
>     status: Value('completed'),
>     endTime: Value(DateTime.now().toUtc()),
>     updatedAt: Value(DateTime.now().toUtc()),
>   ),
> );
> ```

### Question 5: PostGIS LineString vs 1-to-1 Remote Point Tables
*Why is syncing a route as a single PostGIS LineString geometry column vastly superior to synchronizing individual point rows to Supabase?*

> **Answer**:
> 1. **Bandwidth & Latency**: Syncing 3,600 rows requires transmitting ~300 KB of repetitive JSON keys across thousands of rows. Compressing them into a single GeoJSON `LineString` array payload reduces network transfer to ~40 KB and replaces 3,600 HTTP inserts with a single atomic upsert.
> 2. **Database Row Quotas**: Free-tier cloud PostgreSQL databases (like Supabase's 500,000 row quota) would hit capacity after only ~140 workouts if points were stored as rows. With a single LineString column per workout, 140 workouts consume exactly 140 rows.
> 3. **Spatial Query Power**: Storing the track as a `geometry(LineString, 4326)` allows PostgreSQL to utilize native spatial operators with GiST indexing:
>    - `ST_Length(geometry::geography)` for instant distance validation.
>    - `ST_Intersects(geometry, bounding_box)` for sub-millisecond map viewport queries.
>    - `ST_Simplify(geometry, tolerance)` for lightweight downsampled route thumbnails.

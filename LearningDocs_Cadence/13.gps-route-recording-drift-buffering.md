## What this chunk does
This chunk equips Cadence with a continuous GPS tracking engine for outdoor activities (walking, running, cycling). It streams live geographical coordinates via `geolocator`, cleans noisy jitter, calculates real-time distance and pace, buffers coordinate points in RAM, and flushes them to SQLite in optimized transactional batches (`batch.insertAll`) to eliminate flash memory wear and battery drain.

---

## Why it's needed
Outdoor fitness tracking generates high-frequency continuous data (1 GPS reading every 1–3 seconds). Writing every coordinate directly to SQLite disk storage would trigger thousands of filesystem fsync operations, severely draining the device battery and stalling the UI isolate. By combining coordinate filtering with an in-memory buffer and batched database writes, Cadence achieves high-precision route logging with minimal CPU and energy overhead.

## Key concepts

1. **GPS Positioning & Accuracy Filtering**:
   GPS receivers experience multipath interference and satellite signal drift, resulting in inaccurate coordinates with large error margins. We filter incoming `Position` samples using an accuracy threshold (e.g. discarding readings with `accuracy > 25.0` meters) and distance filtering (ignoring jitter under 2 meters when stationary).

2. **The Haversine Formula**:
   Calculates the great-circle distance between two points on a sphere given their latitudes and longitudes:
   $$d = 2R \arcsin \left( \sqrt{\sin^2\left(\frac{\Delta \phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta \lambda}{2}\right)} \right)$$
   where $\phi$ is latitude in radians, $\lambda$ is longitude in radians, and $R = 6,371,000\text{ m}$ is the Earth's mean radius.

3. **In-Memory Buffering & Batch Persistence**:
   Instead of executing an `INSERT INTO route_points` on every GPS tick, coordinates are queued in an in-memory Dart list (`_buffer`). When the buffer reaches a batch threshold (e.g. 10 points) or a timer expires (e.g. every 10 seconds), or when recording is paused/stopped, the buffer is atomically flushed to SQLite using Drift's `batch((b) => b.insertAll(...))`.

4. **Android 14+ Foreground Service Location Requirements**:
   Android 14 (API 34) mandates `android:foregroundServiceType="location"` and runtime permissions (`ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `FOREGROUND_SERVICE_LOCATION`) for any background location task.

## Plain-English Pseudocode (Before Syntax)

```text
ON USER CLICKS 'Start Route':
    1. Check location services enabled. If disabled, prompt user.
    2. Check location permissions. If denied, request permission. If denied forever, show error.
    3. Generate new UUID for route.
    4. Create Route row in Drift with status = 'recording', startTime = NOW().
    5. Set state = Recording(routeId, duration=0, distance=0, pace=0, points=[]).
    6. Start 1-second periodic ticker for duration.
    7. Start GPS stream subscription (distanceFilter = 2 meters).
    8. Update Foreground Notification to 'Recording Route...'.

ON GPS POSITION RECEIVED(newPos):
    1. IF newPos.accuracy > 25.0 meters:
           SKIP (Inaccurate reading / GPS drift)
    2. IF previousPos IS NOT NULL:
           d = calculateHaversineDistance(previousPos, newPos)
           IF d < 2.0 meters:
               SKIP (Stationary noise)
           totalDistance += d
           currentPace = (elapsedSeconds) / (totalDistance / 1000)
    3. Add newPos to _inMemoryBuffer.
    4. IF _inMemoryBuffer.length >= 10 OR (currentTime - lastFlushTime) >= 10 seconds:
           FLUSH BUFFER TO SQLITE.

ON FLUSH BUFFER:
    1. IF _inMemoryBuffer IS EMPTY: RETURN.
    2. Within SQLite TRANSACTION:
           BATCH INSERT all points in _inMemoryBuffer into route_points.
           UPDATE routes SET totalDistanceMeters = totalDistance, durationSeconds = elapsed WHERE id = routeId.
    3. Clear _inMemoryBuffer.
    4. Update lastFlushTime = NOW().

ON USER CLICKS 'Pause Route':
    1. Pause GPS subscription and timer.
    2. Flush any remaining points in _inMemoryBuffer.
    3. Update routes table status = 'paused'.

ON USER CLICKS 'Finish Route':
    1. Cancel GPS subscription and timer.
    2. Flush all remaining points in _inMemoryBuffer.
    3. Calculate final average pace and end time.
    4. Update routes table status = 'completed', endTime = NOW().
    5. Reset state to Idle.
```

## The Edge Case & Error Matrix

| Input / Condition | Failure Mode | Handling Component | Outcome / Action |
|---|---|---|---|
| Location services disabled on device | App cannot acquire GPS signal | `RouteRecordingNotifier` | Prompts user to enable GPS; cancels tracking with informative snackbar. |

| App paused / sent to background | OS throttles background location | Foreground Service (`location`) | Persistent notification keeps location isolate alive. |

| Zero distance logged on finish | Division by zero in pace calculation | `PaceCalculator` | Gracefully sets pace to `0.0` or `--'--"`. |

## Why NOT Do It This Other Way?

- **Anti-Pattern 1: Direct insert per GPS point**:
  - *Why beginners do it*: Calling `database.into(routePoints).insert(pt)` inside `geolocator.listen` seems straightforward.
  - *Why it fails*: GPS emits 1-2 points per second. Each individual insert commits a transaction to SQLite, executing a disk write and WAL sync. Over a 1-hour run (3,600+ writes), this causes high CPU usage, thermal throttling, and battery drain.
  - *Our solution*: 10-point / 10-second memory buffering with atomic `batch.insertAll`.

- **Anti-Pattern 2: Relying on `Geolocator.distanceBetween` in loops without filtering**:
  - *Why beginners do it*: Summing raw distances between all points.
  - *Why it fails*: When sitting still at a traffic light, GPS drift of 3–5 meters back and forth will add 100+ meters of "ghost movement".
  - *Our solution*: Accuracy threshold filtering and minimal displacement gate ($> 2.0\text{ m}$).

## How it works

1. **Lifecycle Management**:
   The `RouteRecordingNotifier` state machine has 4 states: `idle`, `recording`, `paused`, and `completed`.
2. **Buffer Flush Cycle**:
   - `_buffer` holds `List<RoutePointsCompanion>`.
   - On each valid point: `_buffer.add(...)`.
   - If `_buffer.length >= 10` or a periodic 10-second flush timer triggers, a flush transaction executes.
   - When the user presses Pause or Stop, an immediate force-flush occurs.
3. **Pace Formatting**:
   - Pace is expressed in minutes and seconds per kilometer (e.g., $5'24"/km$).
   - Seconds per km = `durationSeconds / (distanceMeters / 1000)`.
   - Minutes = `secondsPerKm ~/ 60`, remaining seconds = `secondsPerKm % 60`.

## Gotchas / trade-offs

- **Background Location Permission on Android 11+**:
  Google Play policy strictly regulates background location (`ACCESS_BACKGROUND_LOCATION`). Using a Foreground Service with `foregroundServiceType="location"` provides foreground location privileges without triggering background location policy restrictions, because the user is actively aware via the ongoing notification.
- **Battery vs Precision Trade-off**:
  We configure `LocationSettings` with `accuracy: LocationAccuracy.high` and `distanceFilter: 2`. Setting distance filter to 0 burns battery unnecessarily; setting it to 10 creates jagged route corners. 2 meters is the sweet spot.

## Check yourself (Inline Evaluation)

1. *Why should GPS coordinates be buffered in memory before writing to SQLite rather than writing each point immediately?*
   - **Answer**: Continuous GPS updates (1–2 Hz) would produce thousands of single-row SQLite transactions, forcing repeated disk I/O and WAL fsync operations that drain battery and slow the UI isolate. Buffering batches the writes into single atomic transactions every 10 points or 10 seconds.

2. *How does the Haversine formula filter out stationary "ghost movement" caused by GPS drift?*
   - **Answer**: By computing the distance between the current position and the previous position, we discard coordinates where the delta is under a minimal displacement threshold (e.g. 2.0 meters) or where horizontal accuracy exceeds 25 meters.

3. *What Android foreground service type and permissions are required on Android 14+ for background route recording?*
   - **Answer**: `android:foregroundServiceType="health|location"` with permissions `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, and `FOREGROUND_SERVICE_LOCATION`.

## Retesting Past Mistakes & Recent Gotchas (Cold Evaluation)

The following questions pull directly from recurring themes in `mistakes.md` and critical architectural lessons learned during Chunks 16–20.

### Question 1: SQLite Sub-Second Snapshot Disambiguation
*Why did point-in-time balance updates in Chunk 20 fail in high-speed widget tests when ordering by `recorded_at DESC, created_at DESC`, and how does adding `tbl.rowId.desc()` eliminate this non-deterministic query behavior?*

> **Answer**:
> In Drift SQLite, `dateTime()` columns are stored as integer unix epoch timestamps in seconds (`unixepoch`). When rapid operations or automated tests execute multiple database inserts within the same calendar second, both `recorded_at` and `created_at` evaluate to identical epoch integer values.
> In SQL, when an `ORDER BY` clause results in ties across all specified sorting columns, the ordering of tied rows is completely undefined by the query planner. If the database engine returns the older initial snapshot before the newer snapshot, key-based deduplication (`latestMap.putIfAbsent`) erroneously retains the stale balance.
> Adding `(tbl) => OrderingTerm.desc(tbl.rowId)` provides a guaranteed monotonic tiebreaker. In SQLite, every row inserted into a standard table is automatically assigned a sequentially increasing 64-bit integer `rowid`. By descending on `rowId`, the most recently inserted row is always guaranteed to appear first, regardless of sub-second execution speeds.

### Question 2: Drift Stream Queries in Riverpod Tests
*Why do test suites hang indefinitely if a developer writes `await container.read(myStreamProvider.future)` on a Drift `.watch()` query, and what is the proper pattern for testing open-ended reactive streams?*

> **Answer**:
> Calling `.future` on a Riverpod `StreamProvider` internally awaits the stream's completion (until `done` or closed). Because Drift's `.watch()` queries return persistent, open-ended reactive streams that continuously observe table modifications and never automatically close, `.future` waits forever and causes the test runner to time out.
> The proper pattern is to subscribe to the provider using `container.listen(provider, (_, _) {})` and then pump microtasks via `await pumpEventQueue();` or pump widget frames. Furthermore, when testing within `testWidgets`, any active Drift stream subscriptions must be unmounted before concluding the test (`await tester.pumpWidget(const SizedBox()); await tester.pump(const Duration(milliseconds: 100));`) to ensure internal debounce and throttle timers cancel cleanly.

### Question 3: Multi-Domain Normalization in Weekly Reviews
*In Chunk 19, we aggregated steps (e.g. 50,000 steps), study time (e.g. 720 minutes), expenses (e.g. $420 spent vs $500 budget), and routine completions (e.g. 85%). Why is naive averaging of raw values mathematically invalid, and how does Cadence normalize heterogeneous domains into a unified 0–100 score?*

> **Answer**:
> Naive averaging or summing raw values across domains is invalid because units of measure and scales differ by orders of magnitude: 50,000 steps would completely dwarf 720 minutes or an 85% routine score, rendering the composite metric meaningless.
> Cadence solves this by applying domain-specific normalization functions that map every dimension to a bounded \([0.0, 100.0]\) float:
> 1. **Movement**: `(totalSteps / weeklyTargetSteps * 100).clamp(0.0, 100.0)`.
> 2. **Study**: `(focusMinutes / targetMinutes * 100).clamp(0.0, 100.0)`.
> 3. **Routines**: `(completedCount / scheduledCount * 100).clamp(0.0, 100.0)`.
> 4. **Finance**: If `spent <= budget`, score is `100.0`; if over budget, score decreases proportionally: `((1.0 - (spent - budget) / budget) * 100).clamp(0.0, 100.0)`.
> The final composite score is calculated as the weighted average of these normalized domain scores, guaranteeing that no single domain can artificially dominate the weekly review.

## Architectural Lessons & Anti-Patterns Avoided

1. **Denormalized Snapshots vs Full Event Sourcing**:
   - *Anti-Pattern*: Recalculating net worth on every app launch by replaying thousands of historical expense and income rows.
   - *Cadence Solution*: Dedicated `account_balances` snapshot table. Financial accounts drift due to interest, market fluctuations, and off-app transactions. Periodic balance snapshots reflect ground truth and make timeline rendering instantaneous.

2. **Decoupled Scoring Engine**:
   - *Anti-Pattern*: Hardcoding aggregation queries directly inside UI widgets or view models.
   - *Cadence Solution*: `WeeklyAggregationService` is a standalone domain service injected via Riverpod. It executes concurrent asynchronous queries across six independent database tables and returns a pure immutable data model (`WeeklySummaryData`), allowing automated headless testing without widget tree dependencies.

3. **Safe Sign Conventions for Debts**:
   - *Anti-Pattern*: Storing debt balances as negative numbers in the database, leading to double-negative subtraction bugs (e.g. `1000 - (-500) = 1500`).
   - *Cadence Solution*: All account balances are stored as positive magnitudes. The `NetWorthSummary` calculator strictly enforces the algebraic invariant:
     \[
     \text{Net Worth} = \sum \text{Assets} - \sum \text{Liabilities}
     \]

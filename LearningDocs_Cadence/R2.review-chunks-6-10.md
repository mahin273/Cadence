## Targeted "Check Yourself" (Cold Retest from mistakes.md)

### Question 1 (From Chunk 10): Partial Updates vs `insertOnConflictUpdate`
**Prompt:** In Drift (SQLite), why does calling `into(table).insertOnConflictUpdate(companion)` fail with an `InvalidDataException` when updating an existing record if non-nullable columns without defaults (such as `createdAt`) are omitted from the Companion? How should partial updates be safely executed instead?

**Answer:**
`insertOnConflictUpdate` translates to raw SQL `INSERT INTO <table> (...) VALUES (...) ON CONFLICT (...) DO UPDATE SET ...`. Because SQLite must evaluate whether an `INSERT` can succeed if no conflict exists, Drift verifies that all required, non-nullable columns without default expressions are present in the Companion. If `createdAt` is omitted, the insert portion of the statement would violate database schema integrity. 
To perform a safe partial update without supplying non-mutated required columns, use Drift's dedicated update statement:
```dart
(update(table)..where((tbl) => tbl.id.equals(id))).write(companion);
```
This produces a clean `UPDATE <table> SET column = ? WHERE id = ?` which only touches the specified fields.

### Question 2 (From Chunk 10): SQLite DateTime Storage & Test Assertions
**Prompt:** How does Drift store `DateTime` values in SQLite by default, and why does an equality test like `expect(event.startTime, originalStartTime.toUtc())` fail in Dart even when both timestamps represent the exact same millisecond?

**Answer:**
Drift by default stores `DateTime` columns as integer timestamps representing Unix epoch in seconds. When Drift reads the integer back from SQLite, its default converter reconstructs a Dart `DateTime` using `DateTime.fromMillisecondsSinceEpoch(seconds * 1000)`. Crucially, this constructor produces a **local** `DateTime` (where `isUtc == false`).
In Dart, the `==` operator on `DateTime` checks both the epoch timestamp **and** the `isUtc` boolean flag. Therefore, a local `DateTime` of `2026-09-08 10:00:00.000` (UTC+6) and a UTC `DateTime` of `2026-09-08 04:00:00.000Z` return `false` on `==`!
To assert date equality correctly across time zone representations:
1. Use `expect(event.startTime.isAtSameMomentAs(expected), isTrue);`
2. Or normalize both sides before comparison: `expect(event.startTime.toUtc(), expected.toUtc());`

### Question 3 (From Chunk 9): Riverpod Stream Providers vs Synchronous Data Derivation
**Prompt:** When building a computed view that depends on multiple database tables (e.g. `dailyGoalsProgressProvider` which reads goals, entries, and expenses), why is deriving state synchronously from upstream stream providers (`.value ?? []`) superior to chaining async `StreamProvider.asyncMap` or `FutureProvider`s?

**Answer:**
Chaining asynchronous streams (`asyncMap` or `FutureProvider`) causes cascading `AsyncLoading` states and unnecessary widget rebuild flickers every time any single table fires an update. In Flutter widget tests, this async chaining frequently results in `pumpAndSettle` timing out because animated loading spinners never settle.
By having raw stream providers expose table lists (`activeGoalsStreamProvider`, `entriesStreamProvider`, `allExpensesStreamProvider`), a downstream `Provider<List<GoalProgress>>` can read `.value ?? []` synchronously. Whenever any underlying stream emits, the derived provider recomputes in microsecond in-memory CPU time and immediately delivers complete, non-null data to the UI with zero loading stutter.

### Question 4 (From Chunk 7 & 8): Database-Level Aggregation & UI Value Clamping
**Prompt:** Why should category expense totals and daily spend sums be computed directly in SQLite via `SUM` and `GROUP BY` rather than loading all raw rows into Dart memory, and what UI defensive check must always accompany progress bars?

**Answer:**
Executing `SELECT category, SUM(amount) ... GROUP BY category` allows SQLite's compiled C core to aggregate thousands of records in microseconds without allocating Dart objects or garbage-collecting thousands of class instances. 
On the UI side, any progress bar (such as `LinearProgressIndicator` or circular gauges) must clamp calculated percentages: `percentage.clamp(0.0, 1.0)`. If a user spends \$600 against a \$500 budget, the raw percentage is `1.2`. Without clamping, Flutter's progress bar paints out of bounds or throws assertion errors in debug mode.
